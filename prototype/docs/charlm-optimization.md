# charlm（自有格式）的優化方向與規格

給 Rust 引擎實作 `charlm-native.md` 時使用。原則只有一條：**優化不能改變數字**。
每一項都要能用 `charlm_vectors.jsonl` 驗證與參考實作一致（標準見最後一節），所以只做「數值上看不出來」的優化。
會改變數字的方向（換量化方式、縮小字表、fp16、跳過重排等）不在這裡；要做就先在原型改、重新評估。

依預期效益排序。

## 1. 少算：快取（效益最大）

### 1a. 前綴快取（以 token 為節點的 trie）

因果模型在位置 i 的一切（每層的 K、V，最後的 `h`）只取決於 `seq[0..=i]`。
建議用 trie 存：每個節點是一個位置，存 6 層的 K、V（各 384 個 f32）、`h`（384 個 f32）與 `lp`（見 1b）。
新序列沿著 trie 走到分歧處，只算之後的位置。

- 每個節點約 20 KB。上限建議 1,024 個節點（約 20 MB），以最近使用來淘汰葉節點。
- 一次重排的候選共用前文與大部分組字內容；下一次按鍵又幾乎全部相同。實測同前文、只換候選的呼叫，
  參考實作從約 30 ms 降到 2–6 ms；Rust 的比例應該類似。
- 快取不能影響結果：參考實作已驗證有快取與完全重算逐位元相同，Rust 版也要測同一件事。

### 1b. 每個位置的 log-probability

`lp[i] = ln P(seq[i+1] | seq[0..=i])` 只取決於 `seq[0..=i+1]`，存在 trie 的位置 i+1 節點上。
輸出層（9,944 × 384，**整個模型最大的一次矩陣乘法**，比一整層 Transformer 還大）只對還沒有 `lp` 的位置計算。
參考實作已經這樣做（`charlm_native.py` 的 `lp`）。

### 1c. 重排結果的快取

`charlm.py` 已經以 (前文, 候選文字) 快取最後的分數（2,000 筆）。Rust 版保留同樣的快取。

## 2. 把候選併成一批

四個線性層與輸出層都是「每一列各自獨立」：啟動值的量化以列（位置）為單位，整數內積精確。
所以同一次重排中，所有候選需要新算的位置可以併成一個矩陣，一層一層往下算：

- 每一層：把所有新位置的 `LN → qkv` 一次算完；注意力**逐候選**算（各自的前綴不同）；
  `proj`、`LN → ff1 → GELU → ff2` 再一次算完。
- 輸出層：所有需要 `lp` 的位置一次算完。
- 好處：權重每讀一次就用在多列上。批次越大越接近「計算受限」而不是「記憶體頻寬受限」，
  在 L3 較小的電腦上差別最明顯。

## 3. 運算核心：int8 矩陣乘法

規格只要求整數結果，加法順序隨意，所以可以自由選擇 SIMD 寫法：

- **權重在載入時重新排列**成運算核心需要的格式（例如每 4／8／16 個輸出列交錯、每 4 個輸入位元組一組），
  只在載入時做一次。
- **有號／無號：** `vpdpbusd` 與 `vpmaddubsw` 都要求一邊是無號 8 位元。做法：`u = qx + 128`（0..=254），
  `acc = Σ u·w − 128·Σw`，`Σw`（每列權重和）載入時先算好。結果是精確整數，與規格相同。
- **AVX-VNNI／AVX-512 VNNI：** 用 `vpdpbusd`（**不要**用會飽和的 `vpdpbusds`）。每組 4 個乘積加進 i32，不會溢位。
- **只有 AVX2：** **不能**用 `vpmaddubsw`：它把兩個 u8×i8 乘積加成 i16 並**飽和**
  （254×127×2 = 64,516 > 32,767），結果會錯。改成把兩邊符號延伸成 i16，用 `vpmaddwd`（i16×i16 → i32 成對相加），
  精確。
- **執行時偵測 CPU**（`is_x86_feature_detected!`），沒有的話用一般的純量版本。所有版本必須給出相同的整數，
  單元測試逐一比對。
- **用 intrinsics，不用手寫組合語言。** 只有在 profiler 證明某個迴圈是瓶頸、而且 intrinsics 編不出需要的指令時，
  才對那一段用 `asm!`。
- **多執行緒：** 輸出層的 9,944 列切給 2 個執行緒（與 ONNX Runtime 目前的設定相同）；其他層的矩陣小，先單執行緒，
  量過再決定。用常駐的執行緒池，不要每次呼叫都建立執行緒。

## 4. 其他步驟（f64）

LayerNorm、注意力分數、softmax、GELU、反量化都規定「內部 f64、結果捨入成 f32」。這些步驟的運算量遠小於矩陣乘法：

- 可以用 AVX2 的 f64 向量（4 個一組）寫，但要注意：**加總的順序改變，f64 結果的最後幾位會不同**，
  捨入成 f32 後幾乎都相同，但不保證。先寫純量版本，與參考實作逐位元一致後，再看 profiler 決定要不要向量化，
  向量化後再用測試向量確認。
- `exp`、`sqrt`：用 Rust 標準庫的 f64 版本（誤差 ≤ 1 ulp），捨入成 f32 後與 numpy 幾乎都相同。
  不要換成低精度的近似版本。
- **例外：輸出層的 logsumexp。** 每個位置要算 9,944 個 `exp`，是這一類裡最重的；它的結果不再捨入成 f32，
  直接進入最後的分數。這裡可以用向量化的 f64 `exp`，只要相對誤差在 1e-15 左右；驗收標準對 `logp` 留了容許值（見最後一節）。

## 5. 記憶體與啟動

- 權重 15 MB，以 int8 常駐；輸入用的 embedding 在用到時才反量化（每個位置一列），不要整張展開成 f32（會多 15 MB）。
- 每次呼叫用預先配置好的暫存空間，不在熱路徑上配置記憶體。
- 載入後先跑一次假的重排（暖機），讓第一個按鍵不用承擔分頁錯誤與快取冷啟動。

## 6. 不建議

- 手寫整段組合語言（見第 3 節）。
- fp16／bf16、縮小字表、改變量化方式：都會改變分數，屬於模型變更，要先在原型評估。
- 「分數差距夠大就跳過重排」：之前評估過，會改變結果。

## 量測方式（優化完成後）

在 Windows 原生環境，Rust 版與 ONNX Runtime 版用相同條件比較：

1. 兩邊都是 2 個執行緒。
2. 用 CPU affinity 綁在**沒有 3D V-Cache 的 CCD** 上（本機的 L3 遠大於一般電腦，會讓數字偏好看）。
3. 熱：連續打字。冷：每次呼叫前讀寫一個 512 MB 的緩衝區把快取洗掉（模擬停頓後的第一個鍵）。
4. 報告每次重排呼叫與每個按鍵的 P50／P95，以**冷的 P95** 為主要判斷；另報告常駐記憶體（working set）。
5. 試用期間看前端 host 的計時紀錄。

採用標準（`charlm-native.md`）：準確率不變差（已達成）、冷的 P95 不比 ONNX Runtime 慢、記憶體不比它多。

## 驗收

- `charlm_vectors.jsonl`：`seqs`、`firsts` 完全相同；`trace`（每層的 `x`）在四捨五入到 6 位小數後完全相同；
  `logp` 每個值與參考實作的差 ≤ 1e-9。
- 有快取與完全重算的結果逐位元相同（Rust 自己的測試）。
- 所有 SIMD 版本與純量版本的整數結果相同（Rust 自己的測試）。
